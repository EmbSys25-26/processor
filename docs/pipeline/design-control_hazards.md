# Control Hazards in Computer Architecture

## 1. What is a Control Hazard?
Control hazards, also known as **branch hazards**, occur primarily with **conditional branch instructions**. 

The pipeline typically assumes that the next instruction to be fetched is the one immediately following it in memory. However, if a branch condition evaluates to `true`, the program must jump to a completely different address. This delay in knowing the "correct" path results in the **improper execution of instructions** that were already in the pipeline.

---

## 2. Why do they occur?
The conflict arises due to the intrinsic delay in the pipeline stages:

* **Instruction Fetch:** The processor starts loading the next instructions automatically.
* **Decoding Stage:** Only here does the processor identify that the instruction is actually a branch.
* **Execution Stage (ALU):** The actual comparison and the calculation of the target address are only completed at this stage.

> **The Problem:** While the branch is being processed in the later stages, the pipeline has already fetched 2 or 3 subsequent instructions by mistake.

---

## 3. How to Resolve Control Hazards?

There are three main strategies used to mitigate these hazards:

### A. Stall

The processor simply stalls the pipeline as soon as it identifies a branch, waiting until the result is known. This resolves the issue but drastically reduces performance.

### B. Flush (Assume Not Take)

The processor assumes the branch will not be taken and continues execution. If it is wrong, the improperly loaded instructions are converted into NOPs and the pipeline is flushed, restarting from the correct address.

### C. Branch Prediction

The processor tries to guess the outcome of a branch before it is executed, based on a history of past executions, to decide whether a branch will be taken. This allows the pipeline to continue fetching instructions without stopping when the prediction is correct.

### Additional Optimization - Early Branch Resolution

This technique moves the branch evaluation logic from the Execution stage to the Decoding stage. By calculating the target address and evaluating the condition earlier in the pipeline, the processor reduces the number of wasted clock cycles.

# Early Branch Resolution – Decode Stage Implementation

The following changes describe the relocation of the calculation and evaluation hardware from the Execute stage to the Decode stage. This allows us to generate the `PCSrcD` signal earlier, updating the PC immediately and clearing the IF/ID register via the `CLR` pin.

As a result, the jump penalty in our processor was optimized from **3 cycles to just 1 cycle**.

---

# Destination Address Calculation in the Decode Stage

Instead of waiting for the ALU in the Execute stage, all the mathematical hardware for calculating where the PC will jump has been moved to the Decode stage.

### Sign Extend Block
This block is needed because the PC has 16 bits and `disp8` only has 8. To connect to the 16-bit adder, the missing bits must be filled in. Instead of adding zeros, the sign bit is copied to preserve negative values in Two's Complement, allowing jumps both forward and backward without changing the offset value.

### << 1 Block
This block converts the distance in instructions to distance in bytes, shifting the value one bit to the left, which is equivalent to multiplying by 2 in digital hardware. It is needed since the PC advances by 2 bytes at a time.

### Imm 16 Extend
This parallel block handles the concatenation of the prefix register with the current immediate to form the address of long absolute jumps, such as `jal`.

### Jump Selection MUX
This block chooses which value will be used to calculate the new PC. Since there are two types of instructions that alter the PC (branches and `jal`), each produces a different target value.

- Input 0 → Relative offset (branches)
- Input 1 → Absolute address (`jal`)

The `is_jal` control signal decides which one goes to the adder:
- If `is_jal = 1` → Selects `jal`
- If `is_jal = 0` → Selects branch

### ID Adder
Adds the offset to `PCPlus2D` (the PC of the current instruction + 2).

The output of this adder is the `PCBranchD` wire, which contains the final jump address.

---

# Condition Evaluation in the Instruction Decode Stage

The decision to *"jump or not jump"* was also moved to the Decode stage, saving precious cycles.

### Condition Logic
This is the brain of the jump. It is a logic block that reads the condition bits from the instruction (`cond[11:7]` extracted from `InstrD`) and compares them with the processor flags.

### PSW Register (Processor Status Word)
This is the status register from which Condition Logic reads the flags generated by the previous instruction.

### br_taken / PCSrcD Signals
If the condition is true, Condition Logic activates the main control signal `PCSrcD`.

---

# The Flush Mechanism

### The CLR Pin
Responsible for the flushing mechanism.

The `PCSrcD` signal generated in Decode travels backwards and connects directly to the `CLR` pin of the pipeline register that separates Fetch from Decode.

By activating `CLR`, all bits in that register are forced to zero, which in practice turns the mistakenly read instruction into a NOP (Bubble).

This ensures that the misprediction penalty is only **1 cycle**.

---

# PC Update

The `PCBranchD` address wire and the `PCSrcD` control wire cross the register barrier and return to the PC input multiplexer.

If `PCSrcD = 1`, the PC ignores `PCPlus2F` and instantly loads the jump address to fetch the correct instruction in the next cycle.

# RAW Hazard on Branches – Flag Dependency

## Why Our ISA is Different

In most textbook processors, RAW hazards on branches are caused by register dependencies — a previous instruction writes a register that the branch reads. In our ISA, **branches do not read registers directly**. They only depend on the processor flags (Z, N, C, V) stored in the PSW register.

This means the classical forwarding multiplexer approach described in most textbooks **does not apply** to our processor. However, a different form of RAW hazard still exists — a **flag RAW hazard**.

## When Does It Occur?

A flag RAW hazard occurs when an arithmetic or logic instruction updates the flags and the very next instruction is a branch that reads those flags. Since the branch decision is now made in the Decode stage, the flags must be ready by then.

Example of a hazardous sequence:

```
ADDI t0, t0, #0   ; updates flags in EX
BEQ  destino      ; reads flags in ID — flags not written yet!
and  ...          ; wrong instruction already fetched
```

In the pipeline, when `BEQ` is in the Decode stage, `ADDI` is in the Execute stage. The flags are only written to the PSW register at the end of EX (on the clock edge), so the Decode stage reads the **old** flag values — producing an incorrect branch decision.

## The IMM Prefix is Safe

It is important to note that the `IMM` prefix instruction does **not** update the flags. Therefore, the sequence `IMM + branch` introduces no flag RAW hazard, regardless of what came before the `IMM`.

```
IMM  #0x400       ; does not touch flags — safe
BEQ  destino      ; flags are still valid from before
```

## Solutions

The flag RAW hazard can be resolved in three ways, ordered from simplest to most optimal:

### Option A — Stall
The pipeline detects that a branch follows a flag-updating instruction and inserts a bubble, waiting one cycle until the flags are correctly written to the PSW register. Simple to implement but wastes one cycle on every such occurrence.

### Option B — Flag Forwarding
The PSW value computed combinationally at the end of the Execute stage is forwarded directly to the Condition Logic in the Decode stage, without waiting for it to be registered. This eliminates the stall but requires additional forwarding logic connecting EX output to the ID comparator.

### Option C — Split-Cycle PSW
The PSW register is written in the first half of the clock cycle and read in the second half. Since the Condition Logic reads the PSW during Decode, and the previous instruction writes the PSW during the first half of the same cycle, the correct flag value is always available with no stall and no forwarding logic needed. This is the most elegant solution for our processor given that the flag update logic is combinational.
